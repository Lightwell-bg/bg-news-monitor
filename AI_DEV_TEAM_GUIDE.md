# AI Dev Team: практическая инструкция

Эта инструкция описывает работу с командой:

- **Lead:** Codex GPT-5.6 Terra, `medium` — координирует работу, выполняет небольшие задачи и принимает результат;
- **Architect:** GPT-6 Astra — подключается только для сложной архитектуры и спорных технических решений;
- **Developer:** Claude Opus, `medium` — пишет и изменяет код;
- **QA/Fixer:** Claude Sonnet, `medium` — проверяет код, воспроизводит и исправляет подтверждённые ошибки в согласованном scope;
- **Reviewer:** GPT-5.6 Sol, `high` — независимо проверяет решение и `git diff`;
- **Scout/Docs:** GPT-5.6 Terra, `medium` — изучает репозиторий и официальную документацию, ничего не меняя;
- **Release:** GPT-5.6 Terra, `medium` — готовит выпуск, Docker, CI/CD, миграции, резервное копирование и откат. Реальный production-деплой запускается только по отдельной команде.

Главный принцип: Lead и агенты — дополнительные инструменты, а не обязательный конвейер. Работа ведётся в VS Code; для T0 и T1 достаточно одного Codex и локальных проверок.

---

## 1. Как устроена работа

Общий процесс:

```text
Идея или ТЗ
    ↓
Codex Lead: уровень задачи, координация и локальные проверки
    ↓
Ваше подтверждение плана
    ↓
Claude Opus Developer: реализация T2/T3
    ↓
Claude Sonnet QA/Fixer: проверки и исправление подтверждённых ошибок
    ↓
Reviewer: ревью только для T3, важного выпуска или по прямой команде
    ↓
При необходимости — один общий список исправлений
    ↓
Release: только подготовка реального выпуска и отката
    ↓
Ваше отдельное разрешение на commit, push и production-деплой
```

Lead хранит основную информацию в трёх файлах:

- `docs/architecture.md` — как устроен проект в целом;
- `docs/current-task.md` — одна текущая задача;
- `docs/decision-log.md` — важные решения и причины их принятия.

Результаты Claude сохраняются автоматически:

- `docs/runs/developer-YYYYMMDD-HHMMSS.txt`;
- `docs/runs/qa-YYYYMMDD-HHMMSS.txt`.

Эти отчёты нужны для проверки и аудита, но не добавляются в Git.

## 2. Что должно быть установлено

На Windows нужны:

1. VS Code.
2. Расширение Codex для VS Code.
3. Git.
4. Python 3.11 или новее. Сейчас используется Python 3.14.
5. Claude Code CLI с выполненной авторизацией.
6. Windows PowerShell 5.1 или PowerShell 7.

Быстрая проверка в PowerShell:

```powershell
git --version
python --version
claude --version
$PSVersionTable.PSVersion
```

Если `claude --version` не работает, сначала необходимо установить или авторизовать Claude Code. Без Claude CLI Lead сможет проектировать и запускать Codex-агентов, но не сможет вызвать Opus Developer и Sonnet QA.

## 4. Главное правило для новых проектов

**Не разрабатывайте все проекты внутри папки `ai-dev-team`.** Используйте её как шаблон.

Для каждого реального проекта создаётся отдельная папка и отдельный Git-репозиторий:

```text
D:\1PythonProjects\ai-dev-team       # шаблон
D:\1PythonProjects\telegram-bot     # отдельный проект
D:\1PythonProjects\crm-agent        # отдельный проект
D:\1PythonProjects\n8n-integration  # отдельный проект
```

Это необходимо, потому что:

- у каждого проекта своя архитектура;
- у каждого проекта своя текущая задача;
- QA и Reviewer должны видеть только изменения этого проекта;
- конфигурация агентов загружается относительно корня открытого репозитория;
- нельзя смешивать отчёты, секреты и Git-историю разных заказчиков.

## 5. Что делать, если есть только идея

Полное ТЗ заранее не обязательно. Достаточно описать идею простыми словами.

Минимальный шаблон:

```text
Название проекта:

Что хочу сделать:

Кто будет пользоваться:

Какую проблему решает:

Что получает пользователь на выходе:

Какие сервисы уже есть:

Какие API или интеграции предполагаются:

Где планируется запуск:

Что обязательно должно войти в первую версию:

Что пока делать не нужно:

Ограничения по бюджету и срокам:

Есть ли персональные данные, платежи, токены или опасные действия:
```

Если часть информации неизвестна, так и напишите. Lead должен сделать разумные предположения и задать только вопросы, без которых нельзя принять важное решение.

### Первый запрос Lead: только проектирование

Вставьте в чат GPT-6:

```text
Работай как Architect / Lead текущего проекта.

Ниже моя идея или ТЗ:

<ВСТАВИТЬ ИДЕЮ ИЛИ ТЗ>

Сейчас нужен только этап проектирования.

1. Проверь текущее состояние Git и структуру репозитория.
2. Определи проблему, пользователей и конечный результат.
3. Раздели обязательный MVP, улучшения на потом и то, что не нужно на старте.
4. Предложи практичный стек и объясни выбор.
5. Опиши компоненты, поток данных, внешние API, хранение данных, авторизацию, ошибки, повторы, логи, безопасность, резервное копирование и откат.
6. При необходимости вызови scout_docs для изучения репозитория или официальной документации.
7. Отделяй подтверждённые возможности API от предположений.
8. Обнови docs/architecture.md.
9. Подготовь одну первую вертикальную задачу в docs/current-task.md с точными критериями приёмки, обязательными проверками и разрешённым списком файлов.
10. Покажи план, риски, открытые вопросы и ожидаемый результат первой задачи.

Не запускай Developer, QA, Reviewer или Release.
Не создавай прикладной код.
Не выполняй git add, commit, push или deployment.
Дождись моего подтверждения архитектуры и первой задачи.
```

На этом этапе Opus не расходуется. Сначала вы проверяете, правильно ли Lead понял идею.

## 6. Как создать новый проект из шаблона

### Вариант A — новый пустой проект

Рекомендуемый способ — локально клонировать чистый шаблон. Git перенесёт только закоммиченные файлы; локальные отчёты и незавершённые изменения шаблона не попадут в новый проект.

Пример для проекта `my-new-project`:

```powershell
Set-Location "D:\1PythonProjects"

git clone `
  "D:\1PythonProjects\ai-dev-team" `
  "D:\1PythonProjects\my-new-project"

Set-Location "D:\1PythonProjects\my-new-project"

git remote -v
git remote remove origin
git status
```

Почему удаляется `origin`: после локального клонирования он указывает на папку шаблона. Новый проект не должен случайно отправлять изменения обратно в `ai-dev-team`.

Если у нового проекта будет GitHub-репозиторий, подключите его позже отдельной командой:

```powershell
git remote add origin https://github.com/USERNAME/REPOSITORY.git
git remote -v
```

Не выполняйте `push`, пока не проверите правильность адреса.

### Вариант B — проект уже существует

Не клонируйте шаблон поверх существующего проекта и не перезаписывайте его `AGENTS.md`, `CLAUDE.md` или `.gitignore` вслепую.

Сначала в существующем проекте:

```powershell
git status --short --untracked-files=all
git log -1 --oneline
```

Если есть незаконченные пользовательские изменения, сначала сохраните их отдельным commit или остановитесь и разберитесь с ними.

Затем откройте существующий проект в Codex и дайте Lead запрос:

```text
Нужно подключить инфраструктуру AI Dev Team к существующему проекту.

Источник шаблона:
D:\1PythonProjects\ai-dev-team

Текущий открытый репозиторий является целевым проектом.

Сначала проведи read-only аудит структуры и Git.
Сравни существующие AGENTS.md, CLAUDE.md, .gitignore, .claude и .codex с шаблоном.

Не перезаписывай существующие инструкции и настройки целиком.
Подготовь точный план объединения и список конфликтов.
Не копируй .git, docs/runs/*.txt, .env, секреты и локальные настройки.
Не запускай агентов и не изменяй файлы до моего отдельного подтверждения.
```

После отчёта разрешайте только перечисленные файлы.

## 7. Что открывать в VS Code

Открывайте **корень конкретного проекта**, а не родительскую папку и не шаблон:

```powershell
code "D:\1PythonProjects\my-new-project"
```

В VS Code:

1. Убедитесь, что в Explorer видны `AGENTS.md`, `.codex`, `.claude`, `docs` и `scripts`.
2. Откройте встроенный PowerShell-терминал.
3. Проверьте путь в приглашении терминала — он должен указывать на нужный проект.
4. Откройте новый чат Codex.
5. Выберите `GPT-6 Astra · Medium`.
6. Выберите режим разрешений `Ask for approval`.

Если `.codex/agents` создавались или изменялись после открытия VS Code:

1. Нажмите `Ctrl + Shift + P`.
2. Выполните `Developer: Reload Window`.
3. Откройте новый чат Codex.

Старый чат может не увидеть новую конфигурацию агентов.

## 8. Подготовка Git перед первой задачей

Перед запуском Developer у проекта должна быть чистая базовая версия:

```powershell
git status --short --untracked-files=all
git log -1 --oneline
```

Для отдельной задачи удобно создать ветку:

```powershell
git switch -c feature/PROJECT-001-short-name
```

Пример:

```powershell
git switch -c feature/CRM-001-lead-webhook
```

Одна задача — одна понятная ветка. Не объединяйте в одну задачу авторизацию, новую админку, рефакторинг базы и деплой, если их можно проверить отдельно.

## 9. Как правильно оформить первую задачу

`docs/current-task.md` должен содержать одну задачу с идентификатором, например:

```text
CRM-001
BOT-001
N8N-001
SITE-001
```

Обязательно зафиксируйте:

- конкретную цель;
- исходную проблему;
- что входит в задачу;
- что не входит;
- какие файлы или компоненты можно менять;
- проверяемые критерии приёмки;
- обязательные команды тестирования;
- ограничения по секретам, API, данным и деплою.

Хороший критерий:

```text
Повтор одного webhook с тем же event_id не создаёт вторую запись.
```

Плохой критерий:

```text
Всё должно работать хорошо.
```

Перед запуском кода прочитайте итог Lead. Если он неверно понял задачу, исправьте архитектуру и `current-task.md` сейчас, а не после работы Developer.

## 10. Как выбрать процесс

Сначала определите уровень задачи:

```text
T0 — документация, конфигурация, небольшая правка: один Codex.
T1 — небольшой скрипт или локальная функция: один Codex и локальные проверки.
T2 — обычная функциональность или интеграция: Opus Developer → Sonnet QA/Fixer.
T3 — платежи, авторизация, персональные данные, миграции, критичная инфраструктура или production: Opus Developer → Sonnet QA/Fixer → Reviewer → Release.
```

Полный T3-конвейер запускается только после явного подтверждения пользователя. Он запрещён для T0 и T1. Для T2 не нужны Reviewer и Release. Scout вызывается только если не хватает сведений о проекте или внешнем API.

Developer и QA/Fixer никогда не работают параллельно. Sonnet исправляет только ошибку, подтверждённую тестами, и после исправления повторяет связанные проверки. Если тесты проходят, повторный запуск Opus не нужен. Не более одного цикла Developer → QA/Fixer допускается без отдельного решения Lead.

Для T0 и T1 не создаются отчёты в `docs/runs`. Сначала выполняйте локальные детерминированные проверки; не запускайте несколько агентов для одинаковой проверки. При исчерпании лимита фиксируется `PAUSED_EXTERNAL_LIMIT`, а не неудачный цикл.

### Какие разрешения подтверждать

Claude Code требует исходящего сетевого подключения. Codex должен сразу запросить разрешение на конкретный запуск:

```text
scripts/run-developer.ps1
```

или:

```text
scripts/run-qa.ps1
```

Разрешайте конкретную команду внутри текущего проекта. Не давайте бессрочное широкое разрешение на любые команды и любые каталоги.

## 11. Ручной запуск Developer и QA

Обычно ими управляет Lead. Но для диагностики скрипты можно запустить вручную.

### Developer

Из корня проекта:

```powershell
powershell.exe `
  -NoProfile `
  -ExecutionPolicy Bypass `
  -File ".\scripts\run-developer.ps1"
```

Developer читает:

- `AGENTS.md`;
- `CLAUDE.md`;
- `docs/architecture.md`;
- `docs/current-task.md`.

Отчёт появится в `docs/runs/developer-*.txt`.

### QA

QA запускается только после завершения Developer:

```powershell
powershell.exe `
  -NoProfile `
  -ExecutionPolicy Bypass `
  -File ".\scripts\run-qa.ps1"
```

Отчёт появится в `docs/runs/qa-*.txt`.

### Другой файл задачи

Оба скрипта принимают параметр `TaskFile`:

```powershell
.\scripts\run-developer.ps1 `
  -TaskFile "docs\tasks\PROJECT-002.md"
```

Но стандартный процесс рассчитан на одну текущую задачу в `docs/current-task.md`. Используйте отдельный файл только осознанно.

## 12. Что делает каждый агент и когда его использовать

| Агент | Когда нужен | Может менять файлы |
|---|---|---:|
| Lead | Координация, небольшая задача и принятие результата | Да, в рамках задачи |
| GPT-6 Astra | Сложная архитектура или спорное техническое решение | По отдельной задаче |
| Developer | Основная реализация T2/T3 | Да, только разрешённые файлы |
| QA/Fixer | Тесты, воспроизведение и исправление подтверждённых ошибок | Да, только исправление в согласованном scope |
| Reviewer | Независимая проверка T3, важного выпуска или по прямой команде | Нет |
| Scout/Docs | Изучение неизвестного репозитория или официального API | Нет |
| Release | Подготовка реального выпуска, деплоя, healthcheck и отката | Только в пределах подготовки выпуска |

### Когда нужен Scout/Docs

Используйте Scout, если:

- проект существующий и структура неизвестна;
- нужно понять чужой код;
- интеграция зависит от актуального внешнего API;
- неизвестны лимиты, scopes, webhooks или требования тарифа;
- Lead не должен тратить дорогой контекст на массовое чтение файлов.

Не запускайте Scout для очевидной правки локального текста или одного понятного файла.

### Когда не нужна вся команда

Не запускайте полный цикл ради:

- исправления опечатки;
- изменения одного заголовка;
- форматирования Markdown;
- небольшой правки комментария;
- действия без изменения логики.

Для T0 и T1 не используйте Claude. Для T2 достаточно Developer → QA/Fixer. Reviewer подключается только для T3, важного выпуска или по прямой команде пользователя.

## 13. Как продолжить работу на следующий день

1. Откройте корень нужного проекта в VS Code.
2. Откройте PowerShell-терминал.
3. Проверьте:

```powershell
git status --short --untracked-files=all
git log -1 --oneline
```

4. Откройте чат Codex GPT-5.6 Terra Lead.
5. Если это новый чат, вставьте:

```text
Продолжи текущую работу в этом репозитории.

Сначала прочитай:
- AGENTS.md
- docs/architecture.md
- docs/current-task.md
- docs/decision-log.md

Затем проверь:
- git status --short --untracked-files=all
- последний commit;
- последние Developer и QA отчёты в docs/runs.

Ничего не изменяй и не запускай агентов, пока не сообщишь:
- текущую задачу и её статус;
- что уже выполнено;
- какие изменения находятся в рабочем дереве;
- какой следующий безопасный шаг.
```

После отчёта подтвердите продолжение.

## 14. Возобновление после лимита Claude

Сообщение вида:

```text
You've hit your session limit · resets ...
```

означает внешний лимит подписки Claude, а не ошибку проекта.

Правильный статус:

```text
PAUSED_EXTERNAL_LIMIT
```

Что делать:

1. Не удалять частично созданные файлы.
2. Не запускать QA на незавершённом результате.
3. Не считать такую попытку циклом исправления.
4. Сохранить неудачный отчёт — это журнал запуска.
5. После времени сброса попросить Lead продолжить ту же задачу.

Готовый запрос:

```text
Возобнови текущую задачу после восстановления лимита Claude.

Сначала проверь git status, docs/current-task.md и последний Developer-отчёт.
Считай существующие файлы частичным и непроверенным результатом.
Не удаляй их автоматически.

Обнови статус задачи с PAUSED_EXTERNAL_LIMIT или BLOCKED на IN_PROGRESS.
Повторный запуск из-за лимита не считай циклом исправления.

Запусти Developer один раз вне sandbox.
После успешного Developer продолжи QA/Fixer. Reviewer и Release добавляй только если уровень задачи — T3, важный выпуск или пользователь попросил их явно.

Не выполняй commit, push или production-деплой.
```

## 15. Типовые ошибки и правильная реакция

### `ConnectionRefused`

Причина: Claude Code попытались запустить внутри сетевой песочницы.

Действие:

- классифицировать как техническую ошибку;
- запросить запуск конкретного PowerShell-скрипта вне sandbox;
- разрешён один повтор;
- успешный повтор получает статус `SUCCESS_WITH_RETRY`.

### Session limit Claude

Действие: остановиться до сброса лимита. Автоматический повтор не выполнять.

### Developer изменил лишние файлы

Действие:

- остановить конвейер;
- показать полный список изменений;
- не запускать QA;
- не отменять изменения автоматически;
- запросить решение пользователя.

### QA/Fixer создал неожиданные файлы

QA/Fixer не создаёт память. Изменения прикладного кода допустимы только для ошибки, подтверждённой тестами, в согласованном scope; после этого QA/Fixer повторяет связанные тесты. Неожиданные файлы или новая функциональность требуют остановки и решения Lead.

### QA или Reviewer нашли ошибку

Lead должен собрать один объединённый список исправлений. QA/Fixer может исправить подтверждённую ошибку сам; повторный Opus не нужен, если тесты после исправления прошли. Если требуется новый Developer, это отдельное решение Lead:

```text
Developer → QA/Fixer
```

Без отдельного решения Lead допускается один цикл Developer → QA/Fixer. Reviewer нужен только для T3, важного выпуска или прямой команды пользователя.

### `git diff` ничего не показывает

Обычный `git diff` не показывает новые untracked-файлы.

Всегда дополнительно выполнять:

```powershell
git status --short --untracked-files=all
```

QA и Reviewer должны отдельно прочитать все новые файлы. Нельзя делать вывод о полном составе работы только по `git diff --stat`.

### Предупреждение в отчёте вместо ответа агента

Иногда Claude CLI пишет предупреждение в `stderr`, которое попадает в отчёт. Нужно отделять:

- фактический ответ агента;
- предупреждения CLI;
- exit code процесса.

Не считать наличие нужного слова достаточным, если задача требует точное содержимое отчёта.

## 16. Как проверить результат перед commit

После статуса `COMPLETED` не выполняйте сразу `git add .`.

Сначала:

```powershell
git status --short --untracked-files=all
git diff --check
git diff
```

Помните: новые файлы нужно проверить отдельно, потому что они не видны в обычном `git diff`.

Дайте Lead запрос:

```text
Подготовь изменения к commit, но пока не выполняй git add и commit.

1. Покажи tracked и untracked файлы.
2. Сопоставь каждый файл с docs/current-task.md.
3. Проверь git diff --check.
4. Проверь отсутствие .env, токенов, ключей, отчётов docs/runs/*.txt и локальных настроек.
5. Составь точный allowlist файлов для commit.
6. Покажи рекомендуемое сообщение commit.

Не выполняй git add, commit или push.
```

После проверки явно разрешите конкретный commit:

```text
Разрешаю добавить в staging только перечисленные файлы и создать локальный commit с сообщением:

feat: <краткое описание>

Не используй git add . или git add -A.
Перед commit проверь git diff --cached --name-only и git diff --cached --check.
Push не выполняй.
```

`push` всегда разрешается отдельно после проверки адреса remote:

```powershell
git remote -v
```

## 17. Подготовка и запуск production

Успешный Release-отчёт не означает, что production уже изменён.

До деплоя Release должен подготовить:

- способ сборки;
- переменные окружения без значений секретов;
- миграции;
- healthcheck;
- проверку логов;
- резервную копию;
- пошаговый откат;
- список команд и ожидаемые результаты.

Сначала попросите только план:

```text
Подготовь production release plan для текущей принятой версии.

Проверь сборку, конфигурацию, миграции, healthcheck, резервное копирование и откат.
Покажи точные команды, риски и точки остановки.

Не выполняй реальный deployment.
Не меняй production.
Не показывай значения секретов.
```

Реальный деплой разрешайте отдельной фразой только после проверки плана, сервера, домена, базы и резервной копии.

## 18. Безопасность

Обязательные правила:

- ключи и токены хранятся только в `.env`, credentials или secret storage;
- `.env` не читается агентами без отдельной реальной необходимости и вашего разрешения;
- `.env` и `.env.*` не коммитятся;
- `.env.example` содержит только имена переменных и пустые примеры;
- webhook защищается секретом или подписью;
- админка закрывается авторизацией;
- персональные данные не копируются в prompts и отчёты без необходимости;
- перед публикацией, платежом, удалением и юридически значимым действием требуется человеческое подтверждение;
- production-деплой, commit и push — три разных разрешения;
- не разрешается одновременное редактирование одних файлов несколькими агентами.

## 19. Экономия лимитов

GPT-6 и Claude Opus не нужно использовать для каждого механического действия.

Практичный режим:

- Codex GPT-5.6 Terra — координация, небольшие задачи и приёмка;
- GPT-6 Astra — только сложная архитектура и спорные решения;
- Scout — массовое чтение и официальная документация;
- Opus Developer — согласованная реализация;
- Sonnet QA/Fixer — проверки и исправление подтверждённых ошибок после реализации;
- Reviewer — независимый контроль только для T3, важного выпуска или по прямой команде;
- Release — только когда действительно есть что выпускать.

Сначала выполняйте локальные проверки. Для T0/T1 не запускайте Claude и не создавайте отчёты. Сначала согласуйте `docs/current-task.md`, затем запускайте Opus только для T2/T3.

## 20. Короткая памятка

### Новый проект

```text
1. Клонировать ai-dev-team в отдельную папку.
2. Удалить origin, ведущий на локальный шаблон.
3. Открыть корень нового проекта в VS Code.
4. Reload Window, если менялась конфигурация агентов.
5. Открыть новый чат Codex: GPT-5.6 Terra Medium.
6. Передать идею или ТЗ и выбрать T0, T1, T2 или T3.
7. Проверить architecture.md и current-task.md.
8. Создать рабочую Git-ветку.
9. Для T3 отдельно подтвердить полный цикл; для T2 запланировать Developer → QA/Fixer.
10. Разрешить по очереди run-developer.ps1 и run-qa.ps1 вне sandbox только если выбран T2/T3.
11. Получить Reviewer и Release только для T3.
12. Проверить tracked и untracked файлы.
13. Отдельно разрешить commit.
14. Отдельно разрешить push.
15. Отдельно разрешить production-деплой.
```

### Продолжение существующей задачи

```text
1. Открыть правильную папку проекта.
2. Проверить git status и последний commit.
3. Попросить Lead прочитать architecture, current-task и последние отчёты.
4. Получить описание текущего состояния.
5. Подтвердить следующий шаг.
```

### Главное

```text
Вы управляете Codex Lead; GPT-6 Astra — отдельный инструмент сложной архитектуры.
Lead выбирает минимальный достаточный процесс.
Одна задача — один current-task.
Сначала план, потом код.
Developer пишет, QA/Fixer проверяет и исправляет подтверждённые ошибки; Reviewer и Release нужны только для T3.
Никто не делает commit, push или production-деплой без отдельного разрешения.
```
